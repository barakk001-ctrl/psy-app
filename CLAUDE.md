# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

"מרפאה" — a Next.js 15 (App Router) practice-management app for solo therapists (psychologists and other therapists): clients, calendar sessions, encrypted clinical notes, per-meeting payments, invoices, PDF receipts, email reminders, reports, message import, PWA. **Hebrew-first, RTL everywhere.** All UI strings, form errors, and emails are Hebrew; locale is hard-coded `he-IL`, timezone `Asia/Jerusalem`, currency ILS. Multi-tenant by design: each user is an isolated practice owner (the app is being prepared for use by many therapists under one deployment).

**UI copy addresses any therapist, not one person** (since 2026-10-29): never feminine-only second person (ברוכה הבאה, כתבי/שלחי, אלייך, את יכולה, הייתה אמורה) and never masculine-only (נסה שוב, היכנס, סמן, ברוך שובך). Use the app's existing neutral styles — impersonal present plural for instructions (״לוחצים״, ״ממלאים״), plural imperative for short prompts (״נסו שוב״, ״כתבו לנו״), nouns for buttons (״שמירה״, ״סימון כהתקיימה״, ״החזרה למתוכננת״), spellings that read either way (״שלך״, ״לך״, ״אותך״), and slashes only where the app already uses them (״לקוח/ה״, ״את/ה״, the legal pages' ״המטפל/ת״). No names or practice-specific examples in UI text (the first user's name appears only in her own data). Error messages point to ״תמיכה״, not to a person.

## Commands

```bash
npm run dev              # dev server (http://localhost:3000)
npm run build            # prisma generate + next build
npm run lint             # eslint
npm run db:migrate       # create + apply a migration in dev (migrations are committed in prisma/migrations/)
npm run db:studio        # Prisma Studio
npm run db:generate      # regenerate Prisma client after schema changes
npm test                 # Vitest — pure-logic tests in src/**/__tests__ (no DB needed; *.db.test.ts skip without TEST_DATABASE_URL)
npm run test:db          # the real-Postgres suites (needs TEST_DATABASE_URL, see scripts/test-db/README.md)
```

CI (`.github/workflows/ci.yml`) runs lint, tsc, tests (with a Postgres service, so the `*.db.test.ts` suites run too), and build on pushes/PRs to main. Testable logic lives in `src/lib` as pure functions — server actions import them; put new business rules there, not inline in actions.

Requires a `.env` (copy from `.env.example`): `DATABASE_URL` (Postgres), `AUTH_SECRET`, and `NOTES_ENCRYPTION_KEY` (base64, exactly 32 bytes — crypto.ts throws otherwise). `RESEND_API_KEY`/`EMAIL_FROM`/`CRON_SECRET` are optional (reminders degrade gracefully). `SUPPORT_EMAIL` (optional) is where help-widget support requests are emailed; unset → `barakk001@gmail.com`. Creating an account (email/password **or** Google) is by invitation: only addresses in `ALLOWED_EMAILS` unless `SIGNUP_OPEN=true` (see **Registration** below); `AUTH_GOOGLE_ID`/`AUTH_GOOGLE_SECRET` (optional) turn on Google sign-in.

**Email** goes only through `sendEmail` (`src/lib/email.ts`, Resend; reads `RESEND_API_KEY` + `EMAIL_FROM`; never throws, returns `{ok:false,error}`). Every failure logs one line `[email] send failed: <provider reason> | code= | status= | from-domain= | to-domain=` (`src/lib/email-log.ts` — domains only, never the recipient address/subject/body), so `railway logs --filter "send failed"` shows the cause. **Production (since 2026-10-13): the domain `mirpaa.app` is verified in Resend (region **eu-west-1**, Ireland; records in Cloudflare DNS, all "DNS only": DKIM TXT `resend._domainkey`, CNAMEs `send` → `send.forge.rmta.net` and `rsend` → `rsend-euw1.forge.rmta.net`, DMARC `_dmarc` `p=none` reporting to barakk001@gmail.com), and `EMAIL_FROM` = `מרפאה אישית <no-reply@mirpaa.app>`, so mail reaches any recipient.** Before that `EMAIL_FROM` was on `resend.dev` and Resend was in testing mode (delivered only to barakk001@gmail.com). The `RESEND_API_KEY` on Railway is **sending-only** — managing domains needs the dashboard (resend.com, Barak's login) or a full-access key. Since late October 2026 the root has MX records for Cloudflare Email Routing (`route1-3.mx.cloudflare.net`), so addresses such as `barak@mirpaa.app` (the operator contact on the legal pages) can receive mail — where they forward is set in Cloudflare, not here. no-reply@ is still only a sender; support replies go to the sender through `replyTo`.

## Architecture

### Mutations are server actions, not API routes

All business mutations live in `src/server/actions/*` (`"use server"` files): `clients`, `sessions`, `notes`, `invoices`, `payments`, `settings`, `auth`, `two-factor`, `account`, `files`, `client-documents`, `inbox`, `meeting-types`, `document-numbers`, `todos`, `support`, `waitlist`, `documents`. The only API routes are `/api/auth/[...nextauth]`, `/api/cron/reminders` (Bearer `CRON_SECRET`), `/api/invoices/[id]/pdf`, `/api/clients/[id]/summaries` (a client's summaries as PDF, audit-logged `RECORD_EXPORT`), `/api/reports/income?from=&to=` (income report PDF), `/api/files/[id]` (session attachments), `/api/documents/[id]` (a client document; `?download=1` for an attachment), `/api/support/[id]/attachment` (a support request's screenshot — its sender or an admin), `/api/inbox` (external message ingestion; GET with `?token=&message=` exists as an iOS-Shortcut-friendly fallback), and `/api/account/export` (the whole account as a ZIP, see below).

Every action follows the same pattern — copy it for new actions:
1. `requireUserId()` (local helper in each file: `auth()` → redirect/throw if no session)
2. Parse `FormData` through a Zod schema from `src/server/validators/*`
3. On validation failure, return `{ error: "<Hebrew message>", fieldErrors }` (state object consumed by `useActionState` forms)
4. Every DB query is scoped by `userId` — this is the entire authorization model (no roles; each user is an isolated practice owner)
5. `revalidatePath(...)` then usually `redirect(...)`

**Tenant isolation is tested on a real Postgres** (since 2026-11-01; `src/server/__tests__/`, how to run: `scripts/test-db/README.md`). `isolation.db.test.ts` seeds two made-up practices and runs every case in `isolation-cases.ts` three ways: B on A's ids (A's whole data fingerprint unchanged, no cross-practice row anywhere, nothing of A's in the result, no email sent), a guest the same, and A on A's own ids as a control (it must really work, so a typo can't "pass" by being refused). Each suite refuses any database that isn't local with "test" in its name and never reads `DATABASE_URL`. **`isolation-coverage.test.ts` runs in every `npm test`, no database needed: a new exported action or API route fails it until it has a case (or an entry in `NO_ID_INPUT`/`NO_ID_ROUTES` with the reason; an action that reads an id can't be declared as taking none).** Copy `write-lock.test.ts`'s habit: add the case with the action.

### Auth & security

Auth.js v5 beta (bcryptjs credentials + optional Google), JWT sessions, no DB adapter. Config split: `src/auth.config.ts` (edge-safe, used by `src/middleware.ts`: pages, pinned session cookie, `authorized`/`jwt`/`session` callbacks) vs `src/auth.ts` (Prisma, providers, Google `signIn`/`jwt` callbacks, Node-only). The middleware matcher **excludes `/api`** — API routes must guard themselves (`session?.user?.id` → 401). Route groups: `(auth)` = public login/register/forgot-password/reset-password/verify-email + `/login/two-factor`; `(app)` = protected layout (sidebar + mobile top/tab bars + clinic banner). The `(auth)` layout: form on the right (~42%), brand panel on the left (~58%, `lg+` only) with a therapy-room photo (`src/components/auth/login-room.jpg`, statically imported so it is served from `/_next/static` + `/_next/image`, both outside the middleware; Unsplash License, see `CREDITS.md`) under the `.auth-brand-wash` sage overlay in `globals.css`, tuned so the white text stays WCAG AA (measured ≥5.3:1 for the small text). Every auth page shows the app's mark + wordmark above the form (the only branding on phones, where the panel is hidden), and the panel shows the mark above the large name.

Layered on top: **TOTP 2FA with backup codes** (`two-factor.ts`, settings card; the code check is `src/lib/second-factor.ts`, shared by both login paths), **Face ID / biometric lock overlay** for the installed PWA, password reset via email (`src/lib/password-reset.ts`), and **password change in Settings** (`changePasswordAction`: needs the current password, rate-limited per user, clears any pending reset link, audit-logged `PASSWORD_CHANGE`). Sessions are JWTs, so a change doesn't sign out other devices (they do expire on their own: see automatic sign-out below).

- **Who is signed in** is decided in one place, `src/lib/auth-gate.ts` (pure, tested): a token with `id` = user; a token with `pending2fa` = "2FA pending" (never a user, lapses after 10 min); anything else = guest. The `session` callback returns `user: null` for the last two — explicitly, because next-auth's server-side `auth()` otherwise falls back to the raw token as `user`. So **every guard must check `session?.user?.id`**, never just `session` or `session.user`. The middleware (`gateRequest`) sends a pending session to `/login/two-factor` from every page (server-action POSTs included); API routes 401 it via their `user.id` check.
- **Automatic sign-out after inactivity ("ניתוק אוטומטי")** — rules in `src/lib/idle-timeout.ts` (pure, edge-safe, tested). Per-user `User.idleTimeoutMinutes` (15/30/60, default **30**; Settings → ניתוק אוטומטי, `IdleTimeoutCard` → `updateIdleTimeoutAction`). Two layers:
  - **Server**: the JWT carries a clock — `authTime` (sign-in), `lastSeen` (last request), `idleMinutes`. The `jwt` callback in `auth.config.ts` mints it at sign-in (`freshSessionClock`; Credentials `authorize` and `tokenForGoogleUser` pass the user's setting) and on every request (middleware, `auth()`, `/api/auth/session`) runs `refreshTokenClock`: null — which makes Auth.js clear the cookie — after `idleMinutes + SERVER_IDLE_GRACE_MS` (5 min) without any request, or `ABSOLUTE_SESSION_MS` (12 h) after sign-in however active. So a laptop that slept or a tab reopened hours later asks for the password before any page renders. `session` (JWT, `maxAge` = 65 min, slid on every request) lives in `auth.config.ts` so the middleware re-issues the cookie with the same lifetime. A token with no clock (issued before the feature) starts one instead of being signed out mid-use. A session update may change only `idleMinutes` (a valid option, signed-in token only) — `updateIdleTimeoutAction` uses `unstable_update` so the new setting applies to the current token at once.
  - **Browser**: `IdleGuard` (`components/security/idle-guard.tsx`, in the (app) layout) tracks pointer/keys/touch/wheel/scroll/input and the tab coming back into view, shared across tabs through localStorage (`idle.*` keys + `storage` events). While active it pings `/api/auth/session` at most every `HEARTBEAT_MS` (2 min) — the grace covers that gap — and a ping answered with no user signs out. `IDLE_WARNING_MS` (2 min) before the deadline it shows "עדיין כאן? המערכת תתנתק בעוד m:ss עקב חוסר פעילות" with **המשך** / **התנתק**; while it shows, only המשך (not a drifting mouse) resets the timer. The 12-hour limit gets its own warning (no continue) and fires `ABSOLUTE_CLIENT_LEAD_MS` before the server's. Signing out covers the page at once, saves unsaved work, calls `idleSignOutAction` (`signOut({ redirect: false })`) and does a full load of `/login?reason=idle|absolute` (a sage notice there), so nothing of the page stays in memory. In the installed PWA the page is also covered while hidden (app-switcher snapshot / first frame on return).
  - **Unsaved work**: editors register through `useUnsavedWork` (`src/lib/unsaved-work.ts` registry). The note editor does: the warning says the summary will be saved, and it is saved (normal `saveNoteAction`, encrypted + audit-logged) before signing out — never an emptied textarea (`noteDraftToKeep`, that would delete the note). Other tabs wait (`idle.saving.<tab>`) for a tab that is still saving. Just before leaving the page the guard calls `markLeavingPage()`, so an editor's "leave this page?" prompt (`isLeavingPage()`) never holds the signed-out screen open. Nothing clinical is ever written to browser storage.
- **Session cookie name is pinned** to `authjs.session-token` (`auth.config.ts` `cookies`). Auth.js would otherwise pick `__Secure-…` whenever the site URL is https, and a rename signs everyone out. Don't change it. Cookies are per host, so each address (below) has its own sign-in.
- **Two public addresses, one per-request origin** (`src/lib/request-origin.ts`, tested). The app answers on `https://mirpaa.app` (canonical, `APP_URL`) and the old `https://psy-app-production.up.railway.app` (the iPhone PWA was installed from it), listed in `APP_ALT_ORIGINS` (comma-separated). **Don't rely on `RAILWAY_PUBLIC_DOMAIN`** for the old address: once a custom domain exists Railway sets it (and `RAILWAY_STATIC_URL`) to `mirpaa.app`. Remove the old address from `APP_ALT_ORIGINS` only when it is retired. `www.mirpaa.app` 308s to the apex (`next.config.ts` `redirects`). **`NEXTAUTH_URL`/`AUTH_URL` must stay unset in production**: Auth.js pins every request to that one origin, which would send sign-ins from the other address to the wrong host (no cookie there). Instead, behind Railway's proxy — where Next hands the middleware and route handlers a `localhost:8080` URL — `withPublicOrigin` rebuilds the request URL from `x-forwarded-host`/`host` + `x-forwarded-proto`, only for a trusted origin (anything else → the canonical one); it wraps the middleware (`src/middleware.ts`) and `/api/auth/[...nextauth]`. Server-side `signIn`/`auth()` read the Host header themselves. `trustHost: true` is set in `auth.config.ts` (explicitly — an empty `AUTH_URL` would otherwise switch host trust off). Emailed links use `canonicalOrigin()` (reset → mirpaa.app); the Grow payment return/notify URLs use the request's origin. Face ID lock (`src/lib/biometric.ts`) registers with `rp.id = location.hostname` and keeps its credential id in localStorage, so it is per address: on mirpaa.app it is simply off until enabled again in Settings (nothing breaks). The ICS calendar feed and the inbox token URLs shown in Settings use the address being viewed — subscriptions made on the old address keep working while it is served.
- **Legal pages** (public, `gateRequest` lets both through; all three render through `components/legal/legal-page.tsx` — one page that scrolls as a whole, a sticky title bar with "חזרה" (`history.back()`, else close the tab the sign-up form opened, else `/login`) and a "לראש העמוד" button after scrolling. `globals.css` sets `overflow-x: clip` on html/body **only for these pages** (`:has(.legal-page)`): the app-wide `overflow-x: hidden` on both html and body makes `<body>` a scroll container, which breaks `sticky` and was seen to keep iOS Safari from scrolling back to the title. The app's own layout still has that rule — so the (app) mobile top bar's `sticky` doesn't actually stick; changing it there is a visible design change, do it deliberately): `/agreement` — the data-holding agreement (`src/lib/agreement.ts`, accepted at registration, versioned) — `/terms` — the terms of service (`src/lib/terms.ts`) — and `/privacy` — the privacy policy (`src/lib/privacy.ts`; must stay factual — e.g. both services run in the EU; if a region ever changes, update it: hosting regions, providers, cookies, backups). - **The agreement** (`src/lib/agreement.ts`, `AGREEMENT_VERSION` `draft-2026-10` since 2026-10-25 — bumping it shows every user the re-acceptance banner on the dashboard): owner (the therapist) vs holder (the operator, "מרום טכנולוגיות" with `[להשלמה]` details), purpose and confidentiality, security as built, sub-processors (section 3א: Railway EU, Resend, Google sign-in / an external calendar feed, backups in Israel; morning was removed from it on 2026-11-08 together with the integration), breach notice, end of service (copy + deletion within 30 days), self-service export and the recycle-bin/backup retention. - **Registration**: all users are created by `createPracticeUser` (`src/lib/practice-user.ts`: lower-cased email, current agreement and terms accepted, `TRIAL_DAYS` trial). **Who may create an account is one rule, `src/lib/signup-policy.ts`** (pure, tested; since 2026-10-28): `canCreateAccount(email)` — `SIGNUP_OPEN=true` → anyone; otherwise only addresses in `ALLOWED_EMAILS` (comma-separated; production with no list = closed, development with no list = open). It applies to **creating** an account only — email/password (`registerAction`, which answers the same whether or not the address has an account: see **Email verification**), Google (`decideGoogleSignIn` `creationAllowed` → `not-invited` → `/register?google=not-invited`) and the email change in Settings. **Existing users always sign in** (the User row is matched first — Keren and Barak can never be locked out by the list). While `inviteOnly()` (production or a list, and `SIGNUP_OPEN` not set) `/register` shows `InviteOnly` ("ההרשמה כרגע בהזמנה בלבד. לבקשת הצטרפות: barak@mirpaa.app", mailto, "קיבלת הזמנה? להרשמה" → `/register?invite=1` = the form with a "קוד הזמנה" field, still checked on the server) and /pricing's buttons read "בקשת הצטרפות" (→ /register). **To open sign-up for everyone: set `SIGNUP_OPEN=true` on Railway** — one variable, not a secret; nothing else changes.
- **Invite codes** (since 2026-11-01; rules `src/lib/invite-codes.ts`, tested; DB `invite-store.ts`; migration `20261101160000_invite_codes`): inviting someone needs no Railway variable. Settings → **הזמנות** (`AdminInvitesCard`, admins only; actions `src/server/actions/invites.ts`, refused for anyone else) creates a code with an optional note, a number of uses (1 to 50) and an expiry (a week, 30 or 90 days, none), lists the last 50 with their status and uses, copies the link and revokes. The link is `/register?invite=CODE` (`inviteLink`, the canonical address): a good code opens the form with a "קיבלת הזמנה" line; a bad one shows the invite-only page saying so. **The server decides**: `registerAction` and `googleSignIn` check again, and the use is taken by one conditional `UPDATE` (`claimInvite`) in the same transaction that creates the account (`createPracticeUser`, `InviteUnavailable`), so racing sign-ups can't share the last use and a failed creation gives it back. `User.inviteCodeId` records it. A code is used up only when it is what let the account in: an address on `ALLOWED_EMAILS`, `SIGNUP_OPEN` or an existing account uses nothing. Google: the register page's button sends the code, `googleRegisterAction` carries it across the redirect in the 15-min httpOnly `psy_google_invite` cookie, and `googleSignIn` (`src/lib/google-sign-in.ts`, the callback's whole logic, tested on a real Postgres in `google-sign-in.db.test.ts`) checks it. Codes are 12 characters from an alphabet with no look-alikes, stored in plain so the link can be copied again later. The email change in Settings still goes by `canCreateAccount` only, so while sign-up is closed an invited user can't move to an address outside the list.
- **Email verification** (since 2026-11-01; rules `src/lib/email-verification.ts`, tested; DB + mail `email-verification-store.ts`, `verify-email-mail.ts`; migration `20261101140000_email_verification` marked **every existing account verified**). `User.emailVerifiedAt` null = an email/password sign-up that hasn't confirmed its address. **Such an account has no session at all**: the credentials `authorize` throws `EmailNotVerified` after the password was right (so it tells a stranger nothing) and `loginAction` shows the pending screen (`VerifyEmailPending`, with "שליחה מחדש" → `resendVerificationAction`: 3/hour per address, 10/hour per IP, one answer for every address). So nothing further in has to know this state. The link is `/verify-email/<token>`: sha256 hash on the User row, 24 hours, single use, a new one kills the old one. Opening it changes nothing (mail scanners open links); `confirmEmailAction` takes the link **plus the account's password**, then signs the person in. That is what stops someone registering another person's address in advance: the mailbox alone can't adopt a stranger's password, and the mailbox owner uses "שכחת סיסמה?", which replaces it and counts as verified. **Google** proves the address: new Google accounts are created verified, and an unverified account reached through Google is verified with its unproven password dropped (`googleVerifiedUpdate`). **Code sign-in** is not offered before verification: the request sends the link instead of a code, with the same answer. **No enumeration**: `registerAction` answers `{pending}` for a new address, an unverified one (a new link, nothing else changes, the first password stays) and a verified one (a notice to the owner, 2/hour, no link) — always computing the password hash and never waiting for an email (`registrationStep`); a refused address gets the same refusal whether or not it has an account. `requestPasswordResetAction` likewise doesn't wait for its email, so a failed send answers like any other request (only logged, `[reset] send failed`). The sign-up emails never carry the name typed at sign-up: anyone can type any address. Still revealing: the login page's "this account has no password" answer below, which is deliberate help for Google accounts. In development with no mail provider the link is printed to the console. Unverified accounts aren't purged.
- **Google** (`AUTH_GOOGLE_ID` + `AUTH_GOOGLE_SECRET`; provider and "המשך עם Google" buttons exist only when both are set — `isGoogleConfigured`). The `signIn` callback runs `googleSignIn` (`src/lib/google-sign-in.ts`), which applies `decideGoogleSignIn` (`src/lib/google-auth.ts`, tested): requires `email_verified === true`; an existing user with that email (lower-cased) is signed in — that is the account linking, there is no Account table and never a second user per email; a new email is created only if sign-up allows it (`canCreateAccount` or a good invite code, else `/register?google=not-invited`) and the browser accepted the agreement — the register page's Google button (same form as the agreement checkbox) sets the 15-min `psy_google_agreement` cookie via `googleRegisterAction`; without it (e.g. from the login page) the user is sent to `/register?invite=1&google=agreement`. New Google users get `hashedPassword: null` (nullable in the schema). The `jwt` callback mints a fresh token for our user (`tokenForGoogleUser`): with TOTP on it is **pending** (no `id`).
- **Pending 2FA → full session**: `/login/two-factor` → `verifyTwoFactorAction` → `signIn("two-factor")`, a second Credentials provider whose `authorize` takes the user from the current pending session (never the request body), rate-limits (`login-2fa:user:` 8/15 min + the shared `login:ip:` 25/15 min — inside `authorize`, so direct POSTs to the callback are limited too; throws `TwoFactorRateLimited`), and checks the TOTP/backup code. Success replaces the cookie with a normal token. The client-side session-update endpoint can't lift the pending state (on `trigger: "update"` the `jwt` callback takes nothing but a valid `idleMinutes`, and only for a signed-in token — `refreshTokenClock`).
- **One-time code sign-in ("כניסה עם קוד חד פעמי")** — the login page's secondary button opens `/login/code` (form co-located, `force-dynamic`, for the EU-builder manifest bug). Email → `requestLoginCodeAction` → 6-digit code by email → `verifyLoginCodeAction` → `signIn("email-code")`, a third Credentials provider in `auth.ts`. Rules in `src/lib/login-code.ts` (pure, tested): one live code per account on the User row (`loginCodeHash` = HMAC-SHA256 keyed by `AUTH_SECRET`, bound to the user id; `loginCodeExpiresAt` 10 min; `loginCodeAttempts`, thrown away after 5 wrong tries); a new request replaces the old code; `consumeLoginCode` (`login-code-store.ts`) clears it with a write conditional on the hash it read, so a code works exactly once even under a race. Limits: see **Rate limits and abuse** below. **No account enumeration**: the request answers "if the address is registered we sent a code" for any address and doesn't await the send (failures are only logged), and a wrong code gets one generic message. **2FA still applies**: the code proves mailbox control — the same thing a reset link proves — so it replaces the password, never the authenticator; the `jwt` callback treats `email-code` like Google (`tokenForGoogleUser` → pending token with TOTP on → `/login/two-factor`). Every rule of a password session (idle timeout, 12-hour limit, pinned cookie) applies, since the token is minted the same way. **Sending is channel-based** (`src/lib/login-code-channel.ts`): email today; SMS needs a provider factory registered in `SMS_PROVIDERS`, `SMS_PROVIDER` + its keys on Railway, the mobile in `User.loginPhone` (not the invoice `phone`; no Settings field yet) and a "בהודעת SMS" choice on `/login/code` — the steps are in the file header. It depends on email delivery working (see **Email** above).
- **Rate limits and abuse** (since 2026-11-01).
  - **The client IP is `X-Real-IP`, and only that** (`clientIpFrom`, `src/lib/client-ip.ts`, tested). The first `X-Forwarded-For` entry is what the visitor sent on any proxy that keeps it, and a position in that list can't be trusted: Railway says the hop count isn't fixed. Measured on 2026-11-01 from a temporary probe that logged booleans only, on both `mirpaa.app` and the old Railway address, with spoofed `X-Real-IP` and `X-Forwarded-For`: `X-Real-IP` was the true client and the spoofed value never arrived; `X-Forwarded-For` had 2 entries, the first the client and the **last an internal hop**, so "rightmost entry" would put every visitor in one bucket. Railway staff's stated rule (October 2026) is the same, but it isn't a versioned contract, so a missing or unusable header on Railway falls to one shared `unknown` bucket and logs `[client-ip] no usable x-real-ip on Railway` once: if that line ever appears, re-measure. **Not measured**: a visitor reaching the app over IPv6 (none available from the test machine; IPv6 is limited per /64). Do not put a CDN or proxy in front (Cloudflare proxying on, say) without re-measuring: `X-Real-IP` would then be that proxy. Off Railway the last `X-Forwarded-For` entry is used.

### Encrypted clinical notes + audit log

`SessionNote` stores only AES-256-GCM ciphertext (`contentCiphertext`/`contentIv`/`contentTag`) — never plaintext. Encrypt/decrypt via `src/lib/crypto.ts` in server code only. Saving empty content deletes the note.

**Autosave and the version check** (since 2026-11-08; rules `src/lib/note-autosave.ts`, tested; DB suite `notes.db.test.ts`). `NoteEditor` saves on its own `AUTOSAVE_AFTER_MS` (60 s) after the text first differs from the saved text, then again every minute while she writes; also when the page is hidden (`visibilitychange`/`pagehide`, the iPhone app switch), when the editor unmounts (moving to another page of the app; the request still completes) and before an idle sign-out. A desktop close/reload with unsaved text gets the browser's "leave?" prompt. Status under the box: "שומר…", "נשמר אוטומטית ב-HH:MM" (`savedAt` from the server, clinic time), or the error with "ניסיון חוזר" (it also retries by itself after `AUTOSAVE_RETRY_MS`). It never sends an emptied textarea (that deletes; only the button does), never saves on its own over a note the page couldn't decrypt (`readable={false}`), and is the same `saveNoteAction` (read-only lock, owner check, encryption, a `NOTE_SAVE` audit row per save). **Every save carries `baseVersion`** — the note's `updatedAt` ISO the text is based on, `""` for no note (`noteVersion`): the server writes only with a conditional statement on that version (`updateMany where updatedAt = base`; `create` for none, where P2002 means someone was first; `deleteMany` likewise), sets `updatedAt` itself and returns the new version. A mismatch writes nothing and returns `conflict` + `currentVersion`; the editor stops saving on its own and offers "הצגת הסיכום השמור" (reload) or "שמירת הטקסט שכאן במקומו" (saves with `currentVersion` as the base: an explicit overwrite). A form with no `baseVersion` (an older page) saves unconditionally, as before. Automatic saves send `auto=1` and skip `revalidatePath`: a refresh would decrypt and log `NOTE_VIEW` again every minute; the editor keeps its own state and version. The app has no locked/finalised note state. Session file attachments are also stored encrypted (`files.ts`, `/api/files/[id]`; served with nosniff, inline only for PDF/images, audit-logged `FILE_UPLOAD`/`FILE_VIEW`/`FILE_DELETE`).

**Key versions and rotation** (`src/lib/crypto.ts`, since 2026-11-01). Every encrypted value keeps its IV in a string, in all three formats, and the key version sits at the front of it: `k2.<iv>` = key 2, no prefix = key 1, so everything written before still reads. Keys: `NOTES_ENCRYPTION_KEY` is key 1, `NOTES_ENCRYPTION_KEY_V2`, `_V3`… are later ones; the highest present encrypts, all present decrypt. **With only `NOTES_ENCRYPTION_KEY` set (production today) new values are written byte-for-byte as before**, so nothing changes until a second key is added. To rotate: set `NOTES_ENCRYPTION_KEY_V2` (new writes use it at once), `npm run data:reencrypt` (dry by default: counts and test-decrypts) then `-- --apply` (`src/lib/reencrypt.ts`: conditional writes, safe to stop and re-run, an undecryptable value is reported and left alone), repeat the dry run until it reports nothing, and only then remove the old key. Any new encrypted column must be added to `reencrypt.ts` and to the export.

**More fields moving to encrypted columns, expand-only** (`src/lib/sensitive-fields.ts`, since 2026-11-01): `Client.idNumber`, `Client.generalNotes`, `SessionFile.fileName`, `InboxMessage.text`. **New writes go to `*Ciphertext` and leave the plain column empty; reads take the ciphertext when there is one, the plain column otherwise**, always through `clientIdNumber` / `clientGeneralNotes` / `sessionFileName` / `inboxText`. Saving a client (the form sends both fields) converts that row as a side effect. `fileName` and `text` are NOT NULL, so they hold `""` once encrypted. Nothing searches or sorts on these fields (checked: no `contains`, no `orderBy`, and the client-side client search uses names only). **Existing rows are not converted and the plain columns are not dropped**: the backfill (`src/lib/encrypted-fields-backfill.ts`, `npm run data:backfill`) is **on hold until the owner confirms `NOTES_ENCRYPTION_KEY` is saved outside Railway**. Nothing in the app calls it; it is dry by default, and `--copy` (fill the encrypted columns, plain ones stay) and `--clear` (empty the plain columns, only where the encrypted value decrypts to the same text) also need `CONFIRM_KEY_IS_BACKED_UP=yes`. Run it inside the Railway service, so data stays in the EU: `railway ssh --service psy-app`, then `npm run data:backfill`. `Invoice.docClientTaxId` still holds the id number as printed on a document, in the clear, and client names, phones and emails were not part of this move.

### Sessions: recurring series, quick-edit, statuses

`createSessionAction` supports weekly/biweekly series: parent (RRULE in `recurrenceRule`) + children (`parentSessionId`). All create/update/reschedule paths run `findOverlaps` with an `allowOverlap` override.

- **Series length defaults to "קבוע — ללא תאריך סיום"** (open-ended) in the new-meeting form (`seriesMode` = `OPEN`; the form sends `openEnded=on` and no `occurrences`); "מספר פגישות מוגדר" (COUNT, 12 by default) is the other choice. An open series is created `OPEN_ENDED_BATCH` (26) meetings ahead with a rule without `COUNT=`, and the reminders cron tops it up (`topUpOpenEndedSeries`, `src/lib/series-topup.ts`). Whether a series is topped up is the pure `shouldTopUpSeries` (`recurrence.ts`, tested): open rule, client **ACTIVE**, at least one future SCHEDULED meeting left (none = ended deliberately, never resurrected), and the last meeting within `TOPUP_HORIZON_MS` (8 weeks). What is added also depends on the account's subscription (`topUpPolicy`, see **Subscriptions → Trial scheduling window**): trial accounts only inside their 30-day window, expired accounts nothing. A series whose last future meeting passes while the account is expired is treated as ended and won't resume after renewal — it has to be booked again.

- **"Only this meeting" vs "all of [client]'s following meetings"** on a date/time change, in both the calendar popup (`quickEditSessionAction`) and the full edit form (`updateSessionAction`), via `ApplyScopeChoice` (`applyScope=single|future`). It's shown only once the time actually changes and the client has followers. Followers are **not** tied to a series: many standing meetings were booked one by one. They're the client's SCHEDULED meetings after both the edited one and now, in the same **standing slot** (same clinic wall-clock weekday + start time) or the same series. Past, cancelled, completed and one-off meetings at other times never move. Each follower shifts by the same day offset and takes the new start/length. The pure rules live in `src/lib/standing-slot.ts` (tested, DST-safe) and the DB loading in `src/lib/session-scope.ts`. Overlaps are checked (and warned live: `checkOverlapAction` takes `applyScope`) across every moved slot, and reminders are rescheduled for each one. Calendar drag-and-drop deliberately stays single-meeting.
- **Cancelling "and all of [client]'s following meetings"** (calendar popup only): switching "פגישה מבוטלת" on, when the client has later meetings, shows `CancelScopeChoice` ("רק הפגישה הזו" / "כל הפגישות הבאות של X") with the counts inline; the save button becomes "ביטול N פגישות". It is the session page's bulk-delete rules (`loadFutureDeletePlan`) started **after this meeting** (`followingCutoff` = max(meeting start, now), `src/lib/cancel-following.ts`, tested): the edited meeting is kept and CANCELLED; every later meeting of the client (not just the standing slot) leaves the calendar — empty ones deleted, ones holding a note/attachment/payment/app invoice/Morning doc kept and CANCELLED with reminders cancelled; meetings between now and this one and past ones stay. The client's open-ended series are closed (`closeClientOpenSeries`), else the top-up would regrow them after the earlier meetings. Runs in one transaction with the edit, logs `SESSIONS_BULK_DELETE`, sends `cancelFollowingCount` (re-asks if the count grew, `needsFollowingConfirm`), and the popup then shows the result with a link to the client card.
- **Deleting** (session page + popup, `DeleteSessionChoice`, in-page confirm, no `window.confirm`): "this meeting only" (`deleteSessionAction`, logs `NOTE_DELETE` if a note went with it) or "all future meetings of [client]" (`deleteClientFutureSessionsAction`, for a client who left). Bulk delete touches **only meetings starting after now**, and never deletes one holding a note, attachment, payment record, app invoice or Morning doc number: those are kept and set CANCELLED so no reminder goes out (`src/lib/bulk-delete.ts`). The counts are shown before confirming. It logs `SESSIONS_BULK_DELETE`, then lands on the client card with a result notice and the פעיל/לא פעיל toggle.
- **`parentSessionId` is ON DELETE SET NULL**, so deleting a series' first meeting used to orphan the rest (no series anymore, no open-ended top-up). Every delete path now calls `keepSeriesLinked` first, which promotes the earliest surviving child to be the root. Statuses: SCHEDULED/COMPLETED/CANCELLED/NO_SHOW (UI label: "לא התקיימה"). Meeting types are user-defined (`MeetingType`, settings card) with optional **per-type calendar colors**.

- **Forms that can be refused submit by hand, not through `action=`.** React 19 resets every uncontrolled field after a form action runs, so a save refused for an overlap used to wipe the time, rate and note. `session-form.tsx`, `quick-edit-dialog.tsx` and `branding-card.tsx` use `onSubmit` → `preventDefault()` → `startTransition(() => formAction(new FormData(form)))`. Copy that for any form whose save can come back with an error. The session summary editor (`note-editor.tsx`) does the same, and its "שינויים שלא נשמרו" indicator compares the textarea with the last text the server confirmed saving (`isNoteDirty`, `src/lib/note-dirty.ts`, CRLF-insensitive) — that baseline is moved forward inside the action wrapper on success; never derive it from the dirty flag itself (that circular check left the indicator stuck after every save).
- **Overlaps are warned live**: `checkOverlapAction` (read-only, same `findOverlaps` query) is called through `useOverlapWarning` 400 ms after the time stops changing, so the red note and the "אפשר חפיפה" box appear before saving. The save still runs its own check (and checks every slot of a new series, which the live check does not).
- **Moving a meeting's start re-applies the default length** (`defaultSessionMinutes`): the quick-edit end time becomes start + default (`addMinutesToTime`, capped at 23:59), and the edit form's duration resets to the default. Both stay editable.
- **Calendar month view must fit the screen without scrolling**: `fixedWeekCount={false}`, `dayMaxEvents` (fit what the cell holds, then "+N נוספים"), compact pill CSS, and the shell height `calc(100dvh - 9.5rem)`. Controls go in the FullCalendar toolbar (`customButtons`), never on a row of their own.
- **Week and day views fit the screen too** (since 2026-10-27): they show only the hours in use — `hourRange` (`src/lib/calendar-hours.ts`, pure, tested) over the meetings in the visible days (FullCalendar `datesSet` → state): earliest − 1 h to latest + 1 h, at least `MIN_SPAN_HOURS` (8), inside 00–24; no meetings → 08:00–21:00. Days longer than 15 h get hour rows instead of half-hours. Rows shrink to 6px (`font-size/line-height: 0` on `.fc-timegrid-slot` — an empty table cell otherwise keeps a line's height) and `expandRows` stretches them to fill the shell; hour labels hang from their row (`.fc-timegrid-slot-label-frame { height: 0 }`) so they don't set its height; `allDaySlot={false}` (meetings always have times). Events render `.fc-tg-event` (time + name; the week view shows the start time only); on phones the week view puts the name first (smaller, wrapping) so a short row keeps the name. Measured at 390×844, 375×667, 1280×720 and 1440×900: no scrolling in either view. Booking by tapping an empty slot only works inside the shown hours — "פגישה חדשה" takes any time.
- **Israeli holidays** (`src/lib/holidays.ts`): fetched server-side from Hebcal (dates only, CC BY 4.0), cached in memory for a day, an empty map on failure. Shown via `dayCellContent`/`dayHeaderContent` (not as events, so they can't be dragged or opened) when `User.showHolidays` is on — the "☑ מועדי ישראל" toolbar button, saved per account.

### Clients: one status

`ClientStatus` is just ACTIVE / INACTIVE (פעיל / לא פעיל). There used to be a third, ARCHIVED ("מאוחסן"), which only hid a client from lists — the practitioner couldn't tell it from inactive, so migration `20260928000000_merge_archived_into_inactive` turned every archived client into inactive and dropped the value. Status is switched from the client card (`ClientStatusToggle`), the row button on the clients list (`ClientStatusMoveButton`; tabs פעילים / לא פעילים; `?view=archived` still maps to inactive) — both via `setClientStatusAction` — or the edit form's status field (`updateClientAction`). Inactive clients keep their history (past meetings, summaries, invoices); they're left out of the calendar/new-meeting pickers (except when the meeting is booked from their own card) but stay selectable for invoices, message import and Morning-doc assignment (listed after active ones).

**Active → inactive takes the client's future meetings off the calendar** (rules in `src/lib/client-deactivation.ts`, tested; DB loading `loadDeactivationPlan` in `session-scope.ts`). It reuses the bulk-delete safety rules: only meetings starting after now and not already CANCELLED; empty ones are deleted, ones holding a note, attachment, payment record, app invoice or Morning doc number are kept and set CANCELLED (only SCHEDULED ones — a future meeting already marked done/no-show keeps its status), with `cancelSessionReminders` for each (deleted ones' jobs cascade). The client's open-ended series are closed (`closeRecurrenceRule` adds `COUNT=<meetings left>`) so the cron never extends them, and the top-up also skips inactive clients. Everything runs in one transaction with the status change (`saveClient` in `clients.ts`), logs `SESSIONS_BULK_DELETE`, and lands on the card's bulk-delete result notice (`?futureDeleted=&futureKept=&keptWhy=`). **It asks first**: when meetings would be affected, the action does not save but returns `{ confirm: { count, notice } }` (edit form: `state.deactivate`), e.g. "יוסרו 8 פגישות עתידיות מהיומן (2 שיש בהן תיעוד/תשלום יישמרו כמבוטלות)."; all three entry points show it in-page (`DeactivationConfirmPanel`, no `window.confirm`) and resubmit with `confirmDeactivate=<count>`. If more meetings appeared since, it asks again (`needsDeactivationConfirm`); with nothing on the calendar it just switches. An old client that never sends the confirmation can therefore never delete anything. Inactive → active changes nothing on the calendar (deleted meetings don't come back; she books again). The client form submits via `onSubmit` → `startTransition` so a refused save keeps what was typed.

**Deleting a client — the recycle bin (סל מחזור)** (`src/lib/client-trash.ts` rules, tested; `client-trash-data.ts` DB; actions `clientDeletionPreviewAction`/`trashClientAction`/`restoreClientAction`/`purgeClientNowAction` in `clients.ts`; UI `components/clients/client-trash.tsx`). Offered only for **inactive** clients (the card's "מחיקת התיק", the row's "מחיקה" on the לא פעילים tab), with an in-page confirmation listing what goes with it (meetings, summaries, attachments, documents) and, if there are summaries or files, a note that she may be legally required to keep clinical records. **Blocked** (`clientDeletionDecision`) for a client with any app invoice, a meeting marked PAID/with an amount paid, or a Morning document (number on a meeting or a synced doc assigned) — tax records; the UI says so and suggests keeping them inactive. Deleting sets `Client.deletedAt` (migration `20261004120000_client_trash`) and cancels the client's PENDING reminder jobs. **`db` hides deleted clients everywhere** (`src/lib/db.ts`: a Prisma query extension runs every read of Client/Session/SessionNote/SessionFile/ClientDocument/ClientDocumentBlob/ReminderJob through `withLiveFilter`, `src/lib/trash-filter.ts`) — lists, pickers, calendar, ICS feed, dashboards, reports, reminders, top-up; their pages 404. Only the bin uses the unfiltered **`dbAll`** (trash tab, restore, purge, audit-log names). Income: a deletable client has no payments, so "received" never changes; their meetings drop out of "expected" when deleted (not 30 days later) and come back on restore. The `?view=trash` tab lists deleted clients with days left, **שחזור** (back as it was, inactive; reminders of future scheduled meetings re-created) and **מחיקה לצמיתות עכשיו** (own confirmation). After `TRASH_DAYS` (30) `purgeExpiredClients` deletes the client and — via ON DELETE CASCADE — meetings, encrypted notes, attachments, client documents and their blobs (bytea in Postgres, no file storage to orphan — an object-store backend would need explicit deletes first, see `document-storage.ts`) and reminder jobs; run hourly by the in-process maintenance, by the cron route, and for the user whenever the trash tab opens. Purged data leaves the nightly backups as they rotate (30 days). Privacy policy section 7 states this.

**Waiting list ("רשימת המתנה")** — a tab on the clients page (`/clients?view=waitlist`, `WaitlistPanel`, actions in `src/server/actions/waitlist.ts`, rules in `src/lib/waitlist.ts`, tested). `WaitlistEntry` (per user): full name, optional phone, notes **encrypted** (`encryptSecret` — they may hold the referral reason), added date; listed oldest first with "ממתין/ה N ימים" (clinic calendar days). ### Income numbers (dashboard, reports, income PDF)

One set of rules in `src/lib/income.ts` (pure, tested in `income.test.ts`) + `income-data.ts` (DB) + `report-periods.ts` (periods, summary): **received** = app-invoice `Payment`s (dated `paidAt`) + meetings marked PAID without an app invoice (dated by the meeting; no amount typed → the rate) − what credit notes gave back; **expected** = rates of SCHEDULED + COMPLETED meetings. **A document counts as money only once issued** (`COUNTS_AS_MONEY`/`isUnissuedDocument`: a morning id or a typed number; older app invoices count as they always did, draft status included). A meeting on an unissued document counts by its own payment record (`hasInvoice` false). **Open debt has one source, `loadOpenDocuments`** (dashboard, reports, /collect): no drafts, no credit notes, and a receipt not yet issued is taken back out of its invoice's `amountPaid`. **A credit note is a negative entry on its own date** (`loadCreditNoteRefunds`, method `CREDIT_NOTE`): linked, it gives back what really came in on the original (its payments + receipts issued for it), so cancelling an unpaid invoice takes nothing off and a paid one nets to zero across its two dates, once; unlinked, its whole amount. A meeting a credit freed but still marked PAID counts by the meeting. Periods follow the clinic calendar (`clinicMonthRange`), not the UTC server clock. The reports page used to read only `Payment` rows, so a Morning-first practice saw ₪0 everywhere — never compute income anywhere else. There is no expenses model.

### PDFs with Hebrew (`@react-pdf/renderer`)

Besides the invoice PDF: the summaries and income-report PDFs use `components/pdf/rtl-text.tsx` and `pdf-response.ts` (reuses the invoice PDF's lazy Heebo registration). Verified rules: `direction: "rtl"` must be on **every** `<Text>` (it is not inherited from the Page — without it wrapped lines holding English/numbers come out with their halves swapped), and never put `\n` inside a `<Text>` (it corrupts that line's glyphs) — split lines into separate `<Text>`s (`RParagraphs`). Cells like "02.09.26 12:00" get `direction: "ltr"`. **Every render goes through `renderPdf`** (`components/invoices/invoice-pdf.tsx`; used by `pdf-response.ts`, the invoice PDF route and `invoice-email.tsx`): it re-registers Heebo as **fresh font objects** for each document and runs renders one at a time. Reason (fixed 2026-10-28, test `pdf-render.test.ts`): fontkit caches one Glyph per glyph id for the font's lifetime with the code points it was first created with; a summaries PDF created some (e.g. ".") with none, after which every income report in that process failed in textkit's RTL reordering (500, "reading 'id'") until a restart. Don't register fonts once per process again; `Font.reset()` doesn't reload (it keeps the cached load promise) and `Font.clear()` would drop react-pdf's built-in Helvetica, so only the Heebo family is replaced. Buttons use `PdfButton` (`components/ui/pdf-button.tsx`), which hands the file to the share sheet in the installed PWA.

- **"פנייה לתמיכה"** (`support-form.tsx` → `submitSupportRequestAction`, `src/server/actions/support.ts`): name/email/phone prefilled from the account, subject, description, optional screenshot (≤5MB; PNG/JPG/WEBP/GIF/HEIC, checked by declared type **and** the bytes — `checkAttachment`). Rate-limited 5/hour per user and per IP. `submitSupportRequest` (`src/lib/support-request.ts`, tested) **saves first** (`SupportRequest` model; screenshot encrypted with `encryptBuffer`), then emails it through the shared `sendEmail` (`src/lib/support-data.ts`; `replyTo` = the sender) — a failed email never loses the request: the user is told it was saved but not emailed, `emailStatus` = FAILED, and `retryFailedSupportEmails` (hourly maintenance; claimed so it's never sent twice) retries up to `MAX_EMAIL_ATTEMPTS` within 3 days. **Nothing from the practice's records is attached** — only what was typed plus the page type (`sanitizePagePath` replaces ids, drops queries) and the browser's user agent; the form asks not to write client-identifying details. Admins read every request in Settings → "פניות תמיכה" (`AdminSupportRequestsCard`, mark handled / reopen), which is the fallback when email is down. The privacy policy (section 2) mentions support requests.

### Message import & inbox

`/import` parses pasted WhatsApp-style messages into clients/sessions (`src/lib/message-parse.ts`); `/api/inbox` ingests external messages by token (configured in Settings). Imported text can be appended to a session's encrypted note. **Two separate keys** (since 2026-10-29, migration `20261029100000_inbox_api_token`, test `inbox-tokens.test.ts`): `User.inboxToken` is the public appointment-request link `/request/<token>` (shared with clients; the form allows 5/hour per IP) and `User.inboxApiToken` is the private API key for `/api/inbox` (shortcuts/automations, 60/hour per account). Neither works in the other's place — before, anyone with a shared request link could post to the API directly. The migration kept every request link and gave each account a fresh API key, so **an existing iPhone Shortcut must be updated with the new API address from Settings → קליטת הודעות מבחוץ**. Generating fills in only missing keys; "ביטול המפתח" clears both.

### Money, dates, RTL

Money is Prisma `Decimal` — no float math. Format money/dates only via `src/lib/format.ts`. Never parse datetime-local strings with `new Date()` on the server — use `src/lib/timezone.ts` (`fromZonedDateTimeLocal`/`toZonedDateTimeLocal`); the server runs in UTC. The layout is `dir="rtl"`: prefer logical properties (`ms-`/`me-`, `start`/`end`) and test positioned/translated elements — RTL flipping has caused drawer bugs (see mobile-top-bar comments).

## Deployment & data

Railway project **Clinic**: push to `main` auto-deploys service **psy-app** (custom domains `mirpaa.app` + `www.mirpaa.app`, registered at and DNS-managed by Cloudflare, records "DNS only" — CNAME flattening at the apex — with Railway's `_railway-verify` TXTs; Railway issues the certificates); start command runs `prisma migrate deploy`. The database is service **Postgres-EU** (Amsterdam, `europe-west4`), and since 2026-09-30 the **psy-app service runs in the EU too** (`europe-west4-drams3a`; it was in `us-east4`, so every query crossed the Atlantic) — chosen deliberately for privacy-law data locality; **do not** move data to non-EU regions. psy-app's `DATABASE_URL` references `${{Postgres-EU.DATABASE_URL}}`. The old US `Postgres` service was deleted on 2026-09-17 after psy-app was confirmed to reference `Postgres-EU` only; its final pre-migration dump is at `E:\psy-app-backups\psy-OLD-pre-migration-*.dump`. Nightly `pg_dump` backups run from the owner's machine (scheduled task `PsyAppDbBackup` → `E:\psy-app-backups`).

The production PWA is installed on the practitioner's iPhone — after every deploy she must fully close and reopen the app, or she'll report stale-client bugs ("stuck saving").
