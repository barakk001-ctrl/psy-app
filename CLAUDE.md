# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

"מרפאה" — a Next.js 15 (App Router) practice-management app for solo psychologists: clients, calendar sessions, encrypted clinical notes, per-meeting payments, invoices, PDF receipts, email reminders, reports, message import, PWA. **Hebrew-first, RTL everywhere.** All UI strings, form errors, and emails are Hebrew; locale is hard-coded `he-IL`, timezone `Asia/Jerusalem`, currency ILS. Multi-tenant by design: each user is an isolated practice owner (the app is being prepared for use by several psychologists under one deployment).

## Commands

```bash
npm run dev              # dev server (http://localhost:3000)
npm run build            # prisma generate + next build
npm run lint             # eslint
npm run db:migrate       # create + apply a migration in dev (migrations are committed in prisma/migrations/)
npm run db:studio        # Prisma Studio
npm run db:generate      # regenerate Prisma client after schema changes
npm test                 # Vitest — pure-logic tests in src/**/__tests__ (no DB needed)
```

CI (`.github/workflows/ci.yml`) runs lint, tsc, tests, and build on pushes/PRs to main. Testable logic lives in `src/lib` as pure functions — server actions import them; put new business rules there, not inline in actions.

Requires a `.env` (copy from `.env.example`): `DATABASE_URL` (Postgres), `AUTH_SECRET`, and `NOTES_ENCRYPTION_KEY` (base64, exactly 32 bytes — crypto.ts throws otherwise). `RESEND_API_KEY`/`EMAIL_FROM`/`CRON_SECRET` are optional (reminders degrade gracefully). `SUPPORT_EMAIL` (optional) is where help-widget support requests are emailed; unset → `barakk001@gmail.com`. Email/password registration in production is gated by `ALLOWED_EMAILS`; `AUTH_GOOGLE_ID`/`AUTH_GOOGLE_SECRET` (optional) turn on Google sign-in.

**Email** goes only through `sendEmail` (`src/lib/email.ts`, Resend; reads `RESEND_API_KEY` + `EMAIL_FROM`; never throws, returns `{ok:false,error}`). Every failure logs one line `[email] send failed: <provider reason> | code= | status= | from-domain= | to-domain=` (`src/lib/email-log.ts` — domains only, never the recipient address/subject/body), so `railway logs --filter "send failed"` shows the cause. **Production (since 2026-10-13): the domain `mirpaa.app` is verified in Resend (region **eu-west-1**, Ireland; records in Cloudflare DNS, all "DNS only": DKIM TXT `resend._domainkey`, CNAMEs `send` → `send.forge.rmta.net` and `rsend` → `rsend-euw1.forge.rmta.net`, DMARC `_dmarc` `p=none` reporting to barakk001@gmail.com), and `EMAIL_FROM` = `מרפאה אישית <no-reply@mirpaa.app>`, so mail reaches any recipient.** Before that `EMAIL_FROM` was on `resend.dev` and Resend was in testing mode (delivered only to barakk001@gmail.com). The `RESEND_API_KEY` on Railway is **sending-only** — managing domains needs the dashboard (resend.com, Barak's login) or a full-access key. Nothing is received at no-reply@ (no MX on the root); support replies go to the sender through `replyTo`.

## Architecture

### Mutations are server actions, not API routes

All business mutations live in `src/server/actions/*` (`"use server"` files): `clients`, `sessions`, `notes`, `invoices`, `payments`, `settings`, `auth`, `two-factor`, `files`, `client-documents`, `inbox`, `meeting-types`, `morning-docs`, `todos`, `support`, `waitlist`, `documents`. The only API routes are `/api/auth/[...nextauth]`, `/api/cron/reminders` (Bearer `CRON_SECRET`), `/api/invoices/[id]/pdf`, `/api/clients/[id]/summaries` (a client's summaries as PDF, audit-logged `RECORD_EXPORT`), `/api/reports/income?from=&to=` (income report PDF), `/api/files/[id]` (session attachments), `/api/documents/[id]` (a client document; `?download=1` for an attachment), `/api/support/[id]/attachment` (a support request's screenshot — its sender or an admin), and `/api/inbox` (external message ingestion; GET with `?token=&message=` exists as an iOS-Shortcut-friendly fallback).

Every action follows the same pattern — copy it for new actions:
1. `requireUserId()` (local helper in each file: `auth()` → redirect/throw if no session)
2. Parse `FormData` through a Zod schema from `src/server/validators/*`
3. On validation failure, return `{ error: "<Hebrew message>", fieldErrors }` (state object consumed by `useActionState` forms)
4. Every DB query is scoped by `userId` — this is the entire authorization model (no roles; each user is an isolated practice owner)
5. `revalidatePath(...)` then usually `redirect(...)`

### Auth & security

Auth.js v5 beta (bcryptjs credentials + optional Google), JWT sessions, no DB adapter. Config split: `src/auth.config.ts` (edge-safe, used by `src/middleware.ts`: pages, pinned session cookie, `authorized`/`jwt`/`session` callbacks) vs `src/auth.ts` (Prisma, providers, Google `signIn`/`jwt` callbacks, Node-only). The middleware matcher **excludes `/api`** — API routes must guard themselves (`session?.user?.id` → 401). Route groups: `(auth)` = public login/register/forgot-password/reset-password + `/login/two-factor`; `(app)` = protected layout (sidebar + mobile top/tab bars + clinic banner). The `(auth)` layout: form on the right (~42%), brand panel on the left (~58%, `lg+` only) with a therapy-room photo (`src/components/auth/login-room.jpg`, statically imported so it is served from `/_next/static` + `/_next/image`, both outside the middleware; Unsplash License, see `CREDITS.md`) under the `.auth-brand-wash` sage overlay in `globals.css`, tuned so the white text stays WCAG AA (measured ≥5.3:1 for the small text). Every auth page shows the app's mark + wordmark above the form (the only branding on phones, where the panel is hidden), and the panel shows the mark above the large name.

Layered on top: **TOTP 2FA with backup codes** (`two-factor.ts`, settings card; the code check is `src/lib/second-factor.ts`, shared by both login paths), **Face ID / biometric lock overlay** for the installed PWA, password reset via email (`src/lib/password-reset.ts`), and **password change in Settings** (`changePasswordAction`: needs the current password, rate-limited per user, clears any pending reset link, audit-logged `PASSWORD_CHANGE`). Sessions are JWTs, so a change doesn't sign out other devices (they do expire on their own: see automatic sign-out below).

- **Who is signed in** is decided in one place, `src/lib/auth-gate.ts` (pure, tested): a token with `id` = user; a token with `pending2fa` = "2FA pending" (never a user, lapses after 10 min); anything else = guest. The `session` callback returns `user: null` for the last two — explicitly, because next-auth's server-side `auth()` otherwise falls back to the raw token as `user`. So **every guard must check `session?.user?.id`**, never just `session` or `session.user`. The middleware (`gateRequest`) sends a pending session to `/login/two-factor` from every page (server-action POSTs included); API routes 401 it via their `user.id` check.
- **Automatic sign-out after inactivity ("ניתוק אוטומטי")** — rules in `src/lib/idle-timeout.ts` (pure, edge-safe, tested). Per-user `User.idleTimeoutMinutes` (15/30/60, default **30**; Settings → ניתוק אוטומטי, `IdleTimeoutCard` → `updateIdleTimeoutAction`). Two layers:
  - **Server**: the JWT carries a clock — `authTime` (sign-in), `lastSeen` (last request), `idleMinutes`. The `jwt` callback in `auth.config.ts` mints it at sign-in (`freshSessionClock`; Credentials `authorize` and `tokenForGoogleUser` pass the user's setting) and on every request (middleware, `auth()`, `/api/auth/session`) runs `refreshTokenClock`: null — which makes Auth.js clear the cookie — after `idleMinutes + SERVER_IDLE_GRACE_MS` (5 min) without any request, or `ABSOLUTE_SESSION_MS` (12 h) after sign-in however active. So a laptop that slept or a tab reopened hours later asks for the password before any page renders. `session` (JWT, `maxAge` = 65 min, slid on every request) lives in `auth.config.ts` so the middleware re-issues the cookie with the same lifetime. A token with no clock (issued before the feature) starts one instead of being signed out mid-use. A session update may change only `idleMinutes` (a valid option, signed-in token only) — `updateIdleTimeoutAction` uses `unstable_update` so the new setting applies to the current token at once.
  - **Browser**: `IdleGuard` (`components/security/idle-guard.tsx`, in the (app) layout) tracks pointer/keys/touch/wheel/scroll/input and the tab coming back into view, shared across tabs through localStorage (`idle.*` keys + `storage` events). While active it pings `/api/auth/session` at most every `HEARTBEAT_MS` (2 min) — the grace covers that gap — and a ping answered with no user signs out. `IDLE_WARNING_MS` (2 min) before the deadline it shows "עדיין כאן? המערכת תתנתק בעוד m:ss עקב חוסר פעילות" with **המשך** / **התנתק**; while it shows, only המשך (not a drifting mouse) resets the timer. The 12-hour limit gets its own warning (no continue) and fires `ABSOLUTE_CLIENT_LEAD_MS` before the server's. Signing out covers the page at once, saves unsaved work, calls `idleSignOutAction` (`signOut({ redirect: false })`) and does a full load of `/login?reason=idle|absolute` (a sage notice there), so nothing of the page stays in memory. In the installed PWA the page is also covered while hidden (app-switcher snapshot / first frame on return).
  - **Unsaved work**: editors register through `useUnsavedWork` (`src/lib/unsaved-work.ts` registry). The note editor does: the warning says the summary will be saved, and it is saved (normal `saveNoteAction`, encrypted + audit-logged) before signing out — never an emptied textarea (`noteDraftToKeep`, that would delete the note). Other tabs wait (`idle.saving.<tab>`) for a tab that is still saving. Nothing clinical is ever written to browser storage.
- **Session cookie name is pinned** to `authjs.session-token` (`auth.config.ts` `cookies`). Auth.js would otherwise pick `__Secure-…` whenever the site URL is https, and a rename signs everyone out. Don't change it. Cookies are per host, so each address (below) has its own sign-in.
- **Two public addresses, one per-request origin** (`src/lib/request-origin.ts`, tested). The app answers on `https://mirpaa.app` (canonical, `APP_URL`) and the old `https://psy-app-production.up.railway.app` (the iPhone PWA was installed from it), listed in `APP_ALT_ORIGINS` (comma-separated). **Don't rely on `RAILWAY_PUBLIC_DOMAIN`** for the old address: once a custom domain exists Railway sets it (and `RAILWAY_STATIC_URL`) to `mirpaa.app`. Remove the old address from `APP_ALT_ORIGINS` only when it is retired. `www.mirpaa.app` 308s to the apex (`next.config.ts` `redirects`). **`NEXTAUTH_URL`/`AUTH_URL` must stay unset in production**: Auth.js pins every request to that one origin, which would send sign-ins from the other address to the wrong host (no cookie there). Instead, behind Railway's proxy — where Next hands the middleware and route handlers a `localhost:8080` URL — `withPublicOrigin` rebuilds the request URL from `x-forwarded-host`/`host` + `x-forwarded-proto`, only for a trusted origin (anything else → the canonical one); it wraps the middleware (`src/middleware.ts`) and `/api/auth/[...nextauth]`. Server-side `signIn`/`auth()` read the Host header themselves. `trustHost: true` is set in `auth.config.ts` (explicitly — an empty `AUTH_URL` would otherwise switch host trust off). Emailed links use `canonicalOrigin()` (reset → mirpaa.app); the Grow payment return/notify URLs use the request's origin. Face ID lock (`src/lib/biometric.ts`) registers with `rp.id = location.hostname` and keeps its credential id in localStorage, so it is per address: on mirpaa.app it is simply off until enabled again in Settings (nothing breaks). The ICS calendar feed and the inbox token URLs shown in Settings use the address being viewed — subscriptions made on the old address keep working while it is served.
- **Legal pages** (public, `gateRequest` lets both through; all three render through `components/legal/legal-page.tsx` — one page that scrolls as a whole, a sticky title bar with "חזרה" (`history.back()`, else close the tab the sign-up form opened, else `/login`) and a "לראש העמוד" button after scrolling. `globals.css` sets `overflow-x: clip` on html/body **only for these pages** (`:has(.legal-page)`): the app-wide `overflow-x: hidden` on both html and body makes `<body>` a scroll container, which breaks `sticky` and was seen to keep iOS Safari from scrolling back to the title. The app's own layout still has that rule — so the (app) mobile top bar's `sticky` doesn't actually stick; changing it there is a visible design change, do it deliberately): `/agreement` — the data-holding agreement (`src/lib/agreement.ts`, accepted at registration, versioned) — `/terms` — the terms of service (`src/lib/terms.ts`) — and `/privacy` — the privacy policy (`src/lib/privacy.ts`; must stay factual — e.g. both services run in the EU; if a region ever changes, update it: hosting regions, providers, cookies, backups). Both are drafts pending a lawyer's review; `/terms` holds `[להשלמה]` placeholders (operator details; prices are stated as including VAT since 2026-10-14) and is not yet part of the registration acceptance. Keep the terms in step with the product (trial length, prices, no auto-renewal, read-only on expiry).
- **The agreement** (`src/lib/agreement.ts`, `AGREEMENT_VERSION` `draft-2026-10` since 2026-10-25 — bumping it shows every user the re-acceptance banner on the dashboard): owner (the therapist) vs holder (the operator, "מרום טכנולוגיות" with `[להשלמה]` details), purpose and confidentiality, security as built, sub-processors (section 3א: Railway EU, Resend, Google sign-in / an external calendar feed, morning when connected, backups in Israel), breach notice, end of service (copy + deletion within 30 days), self-service export and the recycle-bin/backup retention. The sign-up checkbox links to it in a new tab (bold, underlined, finger-sized tap target), and it is linked from /terms, /privacy, the /pricing footer and the `privacy` help article. Keep it as factual as the privacy policy.
- **Registration**: all users are created by `createPracticeUser` (`src/lib/practice-user.ts`: lower-cased email, current agreement accepted, `TRIAL_DAYS` trial). Email/password registration is gated by `ALLOWED_EMAILS` in production (closed if unset); Google registration is **not** — anyone with a verified Google address may open a practice.
- **Google** (`AUTH_GOOGLE_ID` + `AUTH_GOOGLE_SECRET`; provider and "המשך עם Google" buttons exist only when both are set — `isGoogleConfigured`). The `signIn` callback applies `decideGoogleSignIn` (`src/lib/google-auth.ts`, tested): requires `email_verified === true`; an existing user with that email (lower-cased) is signed in — that is the account linking, there is no Account table and never a second user per email; a new email is created only if the browser accepted the agreement — the register page's Google button (same form as the agreement checkbox) sets the 15-min `psy_google_agreement` cookie via `googleRegisterAction`; without it (e.g. from the login page) the user is sent to `/register?google=agreement`. New Google users get `hashedPassword: null` (nullable in the schema). The `jwt` callback mints a fresh token for our user (`tokenForGoogleUser`): with TOTP on it is **pending** (no `id`).
- **Pending 2FA → full session**: `/login/two-factor` → `verifyTwoFactorAction` → `signIn("two-factor")`, a second Credentials provider whose `authorize` takes the user from the current pending session (never the request body), rate-limits like the password login (`login:email:` 8/15 min shared bucket + `login:ip:` 25/15 min — inside `authorize`, so direct POSTs to the callback are limited too; throws `TwoFactorRateLimited`), and checks the TOTP/backup code. Success replaces the cookie with a normal token. The client-side session-update endpoint can't lift the pending state (on `trigger: "update"` the `jwt` callback takes nothing but a valid `idleMinutes`, and only for a signed-in token — `refreshTokenClock`).
- **One-time code sign-in ("כניסה עם קוד חד פעמי")** — the login page's secondary button opens `/login/code` (form co-located, `force-dynamic`, for the EU-builder manifest bug). Email → `requestLoginCodeAction` → 6-digit code by email → `verifyLoginCodeAction` → `signIn("email-code")`, a third Credentials provider in `auth.ts`. Rules in `src/lib/login-code.ts` (pure, tested): one live code per account on the User row (`loginCodeHash` = HMAC-SHA256 keyed by `AUTH_SECRET`, bound to the user id; `loginCodeExpiresAt` 10 min; `loginCodeAttempts`, thrown away after 5 wrong tries); a new request replaces the old code; `consumeLoginCode` (`login-code-store.ts`) clears it with a write conditional on the hash it read, so a code works exactly once even under a race. Limits: 3 sends / 15 min per email and 10 / hour per IP; the check shares the password login's `login:email:`/`login:ip:` buckets. **No account enumeration**: the request answers "if the address is registered we sent a code" for any address and doesn't await the send (failures are only logged), and a wrong code gets one generic message. **2FA still applies**: the code proves mailbox control — the same thing a reset link proves — so it replaces the password, never the authenticator; the `jwt` callback treats `email-code` like Google (`tokenForGoogleUser` → pending token with TOTP on → `/login/two-factor`). Every rule of a password session (idle timeout, 12-hour limit, pinned cookie) applies, since the token is minted the same way. **Sending is channel-based** (`src/lib/login-code-channel.ts`): email today; SMS needs a provider factory registered in `SMS_PROVIDERS`, `SMS_PROVIDER` + its keys on Railway, the mobile in `User.loginPhone` (not the invoice `phone`; no Settings field yet) and a "בהודעת SMS" choice on `/login/code` — the steps are in the file header. It depends on email delivery working (see **Email** above).
- **Sign-ins are in the access log**: `LOGIN_PASSWORD` (credentials `authorize`), `LOGIN_GOOGLE` / `LOGIN_EMAIL_CODE` (`jwt` callback, full session only), `LOGIN_TWO_FACTOR` (the `two-factor` provider — a pending sign-in is logged when its code is entered, not before).
- **Google-only accounts (no password)**: the password login answers "this account has no password — use Google or שכחת סיסמה?"; the reset-by-email flow sets a first password; Settings shows `sendSetPasswordLinkAction` ("שליחת קישור לקביעת סיסמה" to the account's own email) instead of the change-password form. A signed-in session alone can never set a password.
- Google sign-in errors land on `/login?error=…` (`pages.error`), shown in Hebrew. The Google callback URL is `<origin>/api/auth/callback/google` for the address the sign-in started on; the OAuth client (Google Cloud project prefab-winter-134023, client `290338353411-mskk…`) lists both origins and both callbacks — add a new address there before serving it.

### Encrypted clinical notes + audit log

`SessionNote` stores only AES-256-GCM ciphertext (`contentCiphertext`/`contentIv`/`contentTag`) — never plaintext. Encrypt/decrypt via `src/lib/crypto.ts` in server code only. Saving empty content deletes the note. Session file attachments are also stored encrypted (`files.ts`, `/api/files/[id]`; served with nosniff, inline only for PDF/images, audit-logged `FILE_UPLOAD`/`FILE_VIEW`/`FILE_DELETE`).

**Client documents ("מסמכים" on the client card)** — referral letters, assessments, consent/insurance forms, scans. Rules in `src/lib/client-documents.ts` (pure, tested, also run in the browser before uploading): PDF, DOC, DOCX, JPG, PNG, HEIC/HEIF, ≤ `MAX_DOCUMENT_BYTES` (15MB) per file, up to 20 per batch; the **bytes decide the type** (`sniffDocumentType`: `%PDF-`, OLE2, a ZIP holding `word/document.xml` and no `vbaProject.bin`, image signatures) — the stored extension is corrected to match. Optional category (`REFERRAL`/`ASSESSMENT`/`CONSENT`/`INSURANCE`/`OTHER` → הפניה/אבחון/טופס הסכמה/טופס ביטוח/אחר) and short description. `ClientDocument` holds metadata with the **file name and description encrypted** (`encryptSecret`); the encrypted bytes are in `ClientDocumentBlob` (bytea, its own table so client queries stay light) behind the `DocumentBlobStore` put/get/delete interface (`src/lib/document-storage.ts` — encryption happens above the store, so a future object store, e.g. R2 in the EU, only ever holds ciphertext; Postgres backend `document-storage-pg.ts`). Actions `uploadClientDocumentAction` (one file per call — the card loops), `updateClientDocumentAction` (rename keeps the extension), `deleteClientDocumentAction` in `client-documents.ts`; serving is `serveClientDocument` (`src/lib/client-document-serve.ts`, tested with fakes): 401 without a user, 404 unless id **and** owner match, `Content-Disposition` inline only for PDF/images (Hebrew name via `filename*`), nosniff, `Cache-Control: private, no-store`. Audit: `DOCUMENT_UPLOAD`/`DOCUMENT_VIEW`/`DOCUMENT_DOWNLOAD`/`DOCUMENT_UPDATE`/`DOCUMENT_DELETE` (`AuditLog.documentId`). In the installed PWA, view/download fetch the file and open the share sheet (a "הקובץ מוכן — פתיחה" button if the tap's permission expired during the download). The card keeps its own list from the actions' results (then `router.refresh()` in a transition) — a bare refresh was seen not to repaint the list reliably. **Body limits** (`next.config.ts`): `serverActions.bodySizeLimit` and `middlewareClientMaxBodySize` are both 16mb — the middleware runs on page routes, so server-action POSTs pass through it, and Next otherwise cuts bodies there at 10MB. While uploading, the card fires `signalActivity()` (`ACTIVITY_EVENT` in `idle-timeout.ts`, heard by `IdleGuard`) every 20s, so a long upload never trips the idle sign-out.

**Every access to clinical content is audit-logged** (`src/lib/audit.ts` → `AuditLog` model): note view/save/append/delete, client-record views, client documents and session files (upload/view/download/edit/delete), and a client's trash/restore/purge (`CLIENT_TRASH`/`CLIENT_RESTORE`/`CLIENT_PURGE`, Hebrew labels in `audit-log-card.tsx`). AuditLog has deliberately **no FK relations** so entries outlive their subjects; logging is best-effort (failures never break the page). Users see their own log in Settings ("יומן גישה לרשומות"). Any new code path that decrypts or mutates a note must call `logAudit`.

### Reminder pipeline

`src/lib/reminders.ts` schedules `ReminderJob` rows (24h + 1h before each session) and is called from session create/update/status actions — it cancels/reschedules idempotently, so **any change to session times or status must go through these helpers**. The cron route claims due jobs (optimistic SENT flip), builds Hebrew HTML, sends via Resend (returns `{ok:false}` rather than throwing when unconfigured). `vercel.json` defines a cron (every 5 min) — **but production is Railway, where nothing calls `/api/cron/reminders`**: the Clinic project has only `psy-app` + `Postgres-EU`, no cron service, and the HTTP logs show no hits (checked 2026-10-04). Since 2026-10-04 the **open-ended series top-up runs in the in-process scheduler** (`src/server/maintenance.ts`, hourly; it books meetings and queues reminder jobs but sends nothing). **Reminder emails still do not run in production** — waiting for the practitioner to confirm she wants them (patient consent is hers). Turning them on is the owner's call, not a silent code change: turning it on starts emailing clients, and the first run would send every PENDING job already due (incl. ones for meetings that have passed) unless those are cleared first.

**Scheduled housekeeping runs in-process**: `src/instrumentation.ts` → `startMaintenance()` (`src/server/maintenance.ts`) runs `runMaintenance()` a minute after boot and then hourly in the long-lived Node process (once per process, timers `unref`'d; skipped in the edge runtime and during build). It purges clients 30 days in the recycle bin, tops up open-ended series, and re-sends support-request emails that failed. The cron route calls `runMaintenance()` too; every job must be idempotent.

### Sessions: recurring series, quick-edit, statuses

`createSessionAction` supports weekly/biweekly series: parent (RRULE in `recurrenceRule`) + children (`parentSessionId`). All create/update/reschedule paths run `findOverlaps` with an `allowOverlap` override.

- **Series length defaults to "קבוע — ללא תאריך סיום"** (open-ended) in the new-meeting form (`seriesMode` = `OPEN`; the form sends `openEnded=on` and no `occurrences`); "מספר פגישות מוגדר" (COUNT, 12 by default) is the other choice. An open series is created `OPEN_ENDED_BATCH` (26) meetings ahead with a rule without `COUNT=`, and the reminders cron tops it up (`topUpOpenEndedSeries`, `src/lib/series-topup.ts`). Whether a series is topped up is the pure `shouldTopUpSeries` (`recurrence.ts`, tested): open rule, client **ACTIVE**, at least one future SCHEDULED meeting left (none = ended deliberately, never resurrected), and the last meeting within `TOPUP_HORIZON_MS` (8 weeks). What is added also depends on the account's subscription (`topUpPolicy`, see **Subscriptions → Trial scheduling window**): trial accounts only inside their 30-day window, expired accounts nothing. A series whose last future meeting passes while the account is expired is treated as ended and won't resume after renewal — it has to be booked again.

- **"Only this meeting" vs "all of [client]'s following meetings"** on a date/time change, in both the calendar popup (`quickEditSessionAction`) and the full edit form (`updateSessionAction`), via `ApplyScopeChoice` (`applyScope=single|future`). It's shown only once the time actually changes and the client has followers. Followers are **not** tied to a series: many standing meetings were booked one by one. They're the client's SCHEDULED meetings after both the edited one and now, in the same **standing slot** (same clinic wall-clock weekday + start time) or the same series. Past, cancelled, completed and one-off meetings at other times never move. Each follower shifts by the same day offset and takes the new start/length. The pure rules live in `src/lib/standing-slot.ts` (tested, DST-safe) and the DB loading in `src/lib/session-scope.ts`. Overlaps are checked (and warned live: `checkOverlapAction` takes `applyScope`) across every moved slot, and reminders are rescheduled for each one. Calendar drag-and-drop deliberately stays single-meeting.
- **Cancelling "and all of [client]'s following meetings"** (calendar popup only): switching "פגישה מבוטלת" on, when the client has later meetings, shows `CancelScopeChoice` ("רק הפגישה הזו" / "כל הפגישות הבאות של X") with the counts inline; the save button becomes "ביטול N פגישות". It is the session page's bulk-delete rules (`loadFutureDeletePlan`) started **after this meeting** (`followingCutoff` = max(meeting start, now), `src/lib/cancel-following.ts`, tested): the edited meeting is kept and CANCELLED; every later meeting of the client (not just the standing slot) leaves the calendar — empty ones deleted, ones holding a note/attachment/payment/app invoice/Morning doc kept and CANCELLED with reminders cancelled; meetings between now and this one and past ones stay. The client's open-ended series are closed (`closeClientOpenSeries`), else the top-up would regrow them after the earlier meetings. Runs in one transaction with the edit, logs `SESSIONS_BULK_DELETE`, sends `cancelFollowingCount` (re-asks if the count grew, `needsFollowingConfirm`), and the popup then shows the result with a link to the client card.
- **Deleting** (session page + popup, `DeleteSessionChoice`, in-page confirm, no `window.confirm`): "this meeting only" (`deleteSessionAction`, logs `NOTE_DELETE` if a note went with it) or "all future meetings of [client]" (`deleteClientFutureSessionsAction`, for a client who left). Bulk delete touches **only meetings starting after now**, and never deletes one holding a note, attachment, payment record, app invoice or Morning doc number: those are kept and set CANCELLED so no reminder goes out (`src/lib/bulk-delete.ts`). The counts are shown before confirming. It logs `SESSIONS_BULK_DELETE`, then lands on the client card with a result notice and the פעיל/לא פעיל toggle.
- **`parentSessionId` is ON DELETE SET NULL**, so deleting a series' first meeting used to orphan the rest (no series anymore, no open-ended top-up). Every delete path now calls `keepSeriesLinked` first, which promotes the earliest surviving child to be the root. Statuses: SCHEDULED/COMPLETED/CANCELLED/NO_SHOW (UI label: "לא התקיימה"). Meeting types are user-defined (`MeetingType`, settings card) with optional **per-type calendar colors**.

- **Forms that can be refused submit by hand, not through `action=`.** React 19 resets every uncontrolled field after a form action runs, so a save refused for an overlap used to wipe the time, rate and note. `session-form.tsx`, `quick-edit-dialog.tsx` and `branding-card.tsx` use `onSubmit` → `preventDefault()` → `startTransition(() => formAction(new FormData(form)))`. Copy that for any form whose save can come back with an error. The session summary editor (`note-editor.tsx`) does the same, and its "שינויים שלא נשמרו" indicator compares the textarea with the last text the server confirmed saving (`isNoteDirty`, `src/lib/note-dirty.ts`, CRLF-insensitive) — that baseline is moved forward inside the action wrapper on success; never derive it from the dirty flag itself (that circular check left the indicator stuck after every save).
- **Overlaps are warned live**: `checkOverlapAction` (read-only, same `findOverlaps` query) is called through `useOverlapWarning` 400 ms after the time stops changing, so the red note and the "אפשר חפיפה" box appear before saving. The save still runs its own check (and checks every slot of a new series, which the live check does not).
- **Moving a meeting's start re-applies the default length** (`defaultSessionMinutes`): the quick-edit end time becomes start + default (`addMinutesToTime`, capped at 23:59), and the edit form's duration resets to the default. Both stay editable.
- **Calendar month view must fit the screen without scrolling**: `fixedWeekCount={false}`, `dayMaxEvents` (fit what the cell holds, then "+N נוספים"), compact pill CSS, and the shell height `calc(100dvh - 9.5rem)`. Controls go in the FullCalendar toolbar (`customButtons`), never on a row of their own.
- **Israeli holidays** (`src/lib/holidays.ts`): fetched server-side from Hebcal (dates only, CC BY 4.0), cached in memory for a day, an empty map on failure. Shown via `dayCellContent`/`dayHeaderContent` (not as events, so they can't be dragged or opened) when `User.showHolidays` is on — the "☑ מועדי ישראל" toolbar button, saved per account.

### Billing: morning-first, "מסמך חדש", older app invoices

1. **Morning-first (the practitioner's workflow until now)**: billing happens in Morning (Green Invoice); the app records per-session payment status/method/amount (`paymentStatus` etc. on Session) and the practitioner types Morning document numbers onto the session — separate fields for חשבונית מס, קבלה, and the combined חשבונית מס-קבלה (`morningDocNumber`/`morningReceiptNumber`/`morningInvoiceReceiptNumber` + URL fields, auto-linked to synced Morning docs).
2. **"מסמך חדש" — documents in morning's terms** (`/invoices/new`, since 2026-10-14; rules `src/lib/billing-docs.ts`, DB `src/lib/billing-doc-data.ts`, actions `src/server/actions/documents.ts`, UI `components/invoices/document-form.tsx` / `document-view.tsx` / `document-preview.tsx`). Morning's flow: type → client (name / ת״ז printed on the document, prefilled, editable) + date (+ due date for 305) → income lines (the client's unbilled past meetings — COMPLETED, NO_SHOW, or SCHEDULED in the past — plus free lines; VAT included / added for a VAT-liable business) → receipt lines (bank transfer / Bit / PayBox / card / cash / cheque / PayPal, each with morning's extra details; cheque requires bank+branch+account+number) → notes → **preview** (in-app render always; morning's own PDF via `POST /documents/preview` when connected) → issue. Kinds (`DOC_KINDS`): 305 חשבונית מס, 320 חשבונית מס/קבלה, 400 קבלה, 330 חשבונית זיכוי; an exempt business (`vatLiable` false) gets receipts only; the Settings `morningDocType` (400/320/305) is the starting type. **The app never issues a tax document itself** (registered software must): a document is an `Invoice` row with `docType` — always saved as a draft first; with morning connected `issueStoredDocument` creates it **through morning's API** and stores `morningDocId/Number/Url` on the document and the number on its meetings (`morningDocNumber` / `morningInvoiceReceiptNumber` / `morningReceiptNumber`, only where empty — the manual number fields keep working). Issuing is claimed (`morningIssuedAt`, 2 min) so a double tap can't create two; a request with no answer (`uncertain`) keeps the claim and tells her to check morning first. Without a connection the draft page offers "העתקת הפרטים" (`morningCopyText`), "פתיחה ב-morning" (`https://app.greeninvoice.co.il/incomes/documents/new/<type>` — morning has no documented prefill link) and a field to record the number she got there (`setDocumentMorningNumberAction`). Draft PDFs say "טיוטה … אינה מסמך מס". A receipt for a 305 is made from that invoice's page (`relatedInvoiceId`; linked in morning with `linkType: "link"`, which closes the invoice; the 305's `amountPaid` is raised — the money is counted once, on the receipt's `Payment` rows). A credit note (330) is issued from an issued 305/320 (`creditNoteAction`, `linkType: "cancel"`): the original is set CANCELLED and its meetings are freed for billing. Issued documents can't be edited or cancelled in the app (`cancelInvoiceAction` refuses). Money in this flow is in agorot (integers). `client.emails` is sent **only** when she ticks "ש-morning ישלח ללקוח/ה את המסמך במייל" (`docClientEmail`) — morning emails the document link to those addresses. "אחר" isn't offered (morning's type 11 needs a sub-type).
3. **Older app invoices** (`docType` null, made before 2026-10-14): sequential per-user numbering (`User.nextInvoiceNumber`, allocated in a transaction — the new documents use the same counter), one `InvoiceItem` per session max, `recordPaymentAction` recalculates totals atomically, PDF receipts via `@react-pdf/renderer` (Heebo fonts from `public/fonts` as data-URIs with lazy registration — fragile, check git history before touching). The PDF is a receipt, deliberately **not** a tax invoice. Their page keeps the old payment form and "הפקת קבלה ב-morning" (`issueMorningReceiptAction`, now built with the same payload builder; refuses a payment recorded as "אחר").

Morning integration (`src/lib/morning.ts`; official OpenAPI: https://developers.morning.co/api): per-user API keys (secret encrypted like notes, never sent to the browser) behind **one credential seam, `src/lib/morning-credentials.ts`** (`getMorningCredentials` / `saveMorningCredentials` / `clearMorningCredentials`; `User.morningKeySource` MANUAL = pasted in Settings, PARTNER = delivered by morning's partner program — not built). The token is obtained by `TOKEN_STRATEGIES[source]` in morning.ts (PARTNER returns "not available yet" without any request); the document code only calls `getMorningCredentials`, so adding the partner flow means a way to receive its keys + the PARTNER strategy, nothing else. Partner flow per the public spec: `POST /partners/users/connection {email, url}` (Basic auth with the partner's id:secret) → the user approves by email (3 days) → morning POSTs `{id, email, key{id, secret}}` to our `url`, signed `X-Data-Signature` (HMAC-SHA256 with the partner code) — Best plan and up only. sandbox/production base URLs (`morningSandbox` on User — sandbox has separate keys; mixing causes 401). **Tokens**: OAuth 2.0 client credentials at `https://api.morning.co/idp/v1/oauth/token` (sandbox `https://api.sandbox.morning.dev/...`, body `{grant_type, client_id, client_secret}` → `accessToken`, ~1 h), falling back to the older `POST {base}/account/token` (`{id, secret}`, token in the body or `X-Authorization-Bearer`) so a connection that works keeps working; cached per user+environment+key. `buildMorningDocumentPayload` (tested with mocked HTTP in `morning-documents.test.ts`): document `vatType` 0 (by business type), income `vatType` 1 = included / 0 = added, payment types 1 cash, 2 cheque, 3 card (`cardType` 1 Isracard 2 Visa 3 Mastercard 4 Amex 5 Diners, `dealType` 1/2/3, `numPayments`), 4 transfer, 5 PayPal, 10 app (`appType` 1 Bit, 3 PayBox); a receipt still sends income rows (its meetings when they add up to what was received, else one row). Requests time out after 20 s. Document sync into a general inbox for manual client assignment (`syncMorningDocumentsAction`). **No real morning call is made in tests or development** — API access needs the business's own morning plan (Best and up).

### Clients: one status

`ClientStatus` is just ACTIVE / INACTIVE (פעיל / לא פעיל). There used to be a third, ARCHIVED ("מאוחסן"), which only hid a client from lists — the practitioner couldn't tell it from inactive, so migration `20260928000000_merge_archived_into_inactive` turned every archived client into inactive and dropped the value. Status is switched from the client card (`ClientStatusToggle`), the row button on the clients list (`ClientStatusMoveButton`; tabs פעילים / לא פעילים; `?view=archived` still maps to inactive) — both via `setClientStatusAction` — or the edit form's status field (`updateClientAction`). Inactive clients keep their history (past meetings, summaries, invoices); they're left out of the calendar/new-meeting pickers (except when the meeting is booked from their own card) but stay selectable for invoices, message import and Morning-doc assignment (listed after active ones).

**Active → inactive takes the client's future meetings off the calendar** (rules in `src/lib/client-deactivation.ts`, tested; DB loading `loadDeactivationPlan` in `session-scope.ts`). It reuses the bulk-delete safety rules: only meetings starting after now and not already CANCELLED; empty ones are deleted, ones holding a note, attachment, payment record, app invoice or Morning doc number are kept and set CANCELLED (only SCHEDULED ones — a future meeting already marked done/no-show keeps its status), with `cancelSessionReminders` for each (deleted ones' jobs cascade). The client's open-ended series are closed (`closeRecurrenceRule` adds `COUNT=<meetings left>`) so the cron never extends them, and the top-up also skips inactive clients. Everything runs in one transaction with the status change (`saveClient` in `clients.ts`), logs `SESSIONS_BULK_DELETE`, and lands on the card's bulk-delete result notice (`?futureDeleted=&futureKept=&keptWhy=`). **It asks first**: when meetings would be affected, the action does not save but returns `{ confirm: { count, notice } }` (edit form: `state.deactivate`), e.g. "יוסרו 8 פגישות עתידיות מהיומן (2 שיש בהן תיעוד/תשלום יישמרו כמבוטלות)."; all three entry points show it in-page (`DeactivationConfirmPanel`, no `window.confirm`) and resubmit with `confirmDeactivate=<count>`. If more meetings appeared since, it asks again (`needsDeactivationConfirm`); with nothing on the calendar it just switches. An old client that never sends the confirmation can therefore never delete anything. Inactive → active changes nothing on the calendar (deleted meetings don't come back; she books again). The client form submits via `onSubmit` → `startTransition` so a refused save keeps what was typed.

**Deleting a client — the recycle bin (סל מחזור)** (`src/lib/client-trash.ts` rules, tested; `client-trash-data.ts` DB; actions `clientDeletionPreviewAction`/`trashClientAction`/`restoreClientAction`/`purgeClientNowAction` in `clients.ts`; UI `components/clients/client-trash.tsx`). Offered only for **inactive** clients (the card's "מחיקת התיק", the row's "מחיקה" on the לא פעילים tab), with an in-page confirmation listing what goes with it (meetings, summaries, attachments, documents) and, if there are summaries or files, a note that she may be legally required to keep clinical records. **Blocked** (`clientDeletionDecision`) for a client with any app invoice, a meeting marked PAID/with an amount paid, or a Morning document (number on a meeting or a synced doc assigned) — tax records; the UI says so and suggests keeping them inactive. Deleting sets `Client.deletedAt` (migration `20261004120000_client_trash`) and cancels the client's PENDING reminder jobs. **`db` hides deleted clients everywhere** (`src/lib/db.ts`: a Prisma query extension runs every read of Client/Session/SessionNote/SessionFile/ClientDocument/ClientDocumentBlob/ReminderJob through `withLiveFilter`, `src/lib/trash-filter.ts`) — lists, pickers, calendar, ICS feed, dashboards, reports, reminders, top-up; their pages 404. Only the bin uses the unfiltered **`dbAll`** (trash tab, restore, purge, audit-log names). Income: a deletable client has no payments, so "received" never changes; their meetings drop out of "expected" when deleted (not 30 days later) and come back on restore. The `?view=trash` tab lists deleted clients with days left, **שחזור** (back as it was, inactive; reminders of future scheduled meetings re-created) and **מחיקה לצמיתות עכשיו** (own confirmation). After `TRASH_DAYS` (30) `purgeExpiredClients` deletes the client and — via ON DELETE CASCADE — meetings, encrypted notes, attachments, client documents and their blobs (bytea in Postgres, no file storage to orphan — an object-store backend would need explicit deletes first, see `document-storage.ts`) and reminder jobs; run hourly by the in-process maintenance, by the cron route, and for the user whenever the trash tab opens. Purged data leaves the nightly backups as they rotate (30 days). Privacy policy section 7 states this.

**Waiting list ("רשימת המתנה")** — a tab on the clients page (`/clients?view=waitlist`, `WaitlistPanel`, actions in `src/server/actions/waitlist.ts`, rules in `src/lib/waitlist.ts`, tested). `WaitlistEntry` (per user): full name, optional phone, notes **encrypted** (`encryptSecret` — they may hold the referral reason), added date; listed oldest first with "ממתין/ה N ימים" (clinic calendar days). The phone is a `tel:` link (Israeli numbers as +972) plus a wa.me button. "הפיכה ללקוח" opens `/clients/new?fromWaitlist=<id>` prefilled (`splitFullName`: first word = first name; notes → הערות כלליות); `createClientAction` deletes the entry (scoped by `userId`) **in the same transaction** that creates the client, so cancelling the form keeps it on the list. Not clinical records, so no audit entries. Help article `waitlist`.

The client card splits meetings into פגישות עתידיות / פגישות שהתקיימו / בוטלו-לא התקיימו (`SessionList`). "Took place" = COMPLETED, or SCHEDULED whose time has passed (`tookPlace` in `src/lib/income.ts`) — most meetings are never marked completed.

The old US `Postgres` service was deleted on 2026-09-17 after psy-app was confirmed to reference `Postgres-EU` only; its final pre-migration dump is at `E:\psy-app-backups\psy-OLD-pre-migration-*.dump`. Nightly `pg_dump` backups run from the owner's machine (scheduled task `PsyAppDbBackup` → `E:\psy-app-backups`).

The production PWA is installed on the practitioner's iPhone — after every deploy she must fully close and reopen the app, or she'll report stale-client bugs ("stuck saving").
